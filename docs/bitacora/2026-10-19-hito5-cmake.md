# 2026-10-19 · Hito 5 · Sistema de construcción con CMake y el recompilador como paso de la compilación

## Pregunta de partida

Cómo pasar de un `Makefile` que llamaba a `clang` archivo por archivo (y solo valía en este Mac) a un sistema de
construcción que cubra recompilador, runtime, juego y arneses en macOS, Linux, Windows y Web, con las ROMs del usuario
como única entrada, y cómo saber que el resultado es el mismo que el del Makefile original y no uno parecido.

## Qué se hizo

### Herramientas locales

CMake no estaba instalado ni había Emscripten ni mingw (comprobado con `which`). Siguiendo la regla del usuario (instalar
dentro del proyecto, preguntar antes de tocar el sistema) todo va a `external/`:

| Herramienta | Versión | Origen y comprobación |
|---|---|---|
| CMake | 4.4.4 | binario oficial de Kitware para macOS (`cmake-4.4.4-macos-universal.tar.gz`), SHA-256 contra `cmake-4.4.4-SHA-256.txt` |
| Emscripten (emsdk) | 6.0.13 | `git clone` de emsdk + `emsdk install 6.0.13` (LLVM, Binaryen, Node 24); 1,8 GB |
| llvm-mingw | 20261006 (clang 23.1.3) | tarball de macOS universal, SHA-256 que publica GitHub para el archivo |
| SDL3 para mingw | 3.4.18 | `SDL3-devel-3.4.18-mingw.tar.gz`, SHA-256 de GitHub |

`tools/setup-local-tools.sh [cmake|emsdk|mingw|all]` reproduce las instalaciones con los SHA-256 fijados en el guion (CMake y
mingw/SDL; emsdk descarga de sus propios repositorios). SDL3 en macOS sigue siendo el de Homebrew que ya usaba el visor
(3.4.18); el puerto de SDL3 de Emscripten (3.4.2) lo baja `emcc` a su caché. Docker Desktop ya estaba instalado pero parado:
se arrancó para las pruebas de Linux y se cerró al acabar.

### Estructura de CMake

`CMakeLists.txt` en la raíz y en `third_party/`, `runtime/`, `platform/`, `harness/`, `tools/`, `app/` y `tests/`.

- **Opciones**: `SF2_ROM_DIR` (el `sf2.zip` o la carpeta con las ROMs), `SF2_GENERATED_DIR` (usar C ya generado),
  `SF2_BUILD_APP/HARNESS/TESTS`, y `SF2_BFRAMES`, `SF2_FRAMES`, `SF2_INPUTS`, `SF2_VFRAMES` para los objetivos de validación.
  Tipo por omisión `Release` = `-O2 -g` sin `NDEBUG`, la configuración con la que se validó el sonido bit a bit (D31); no se
  tocan `-ffp-contract` ni `-ffast-math`.
- **Bibliotecas**: `sf2_base` (memoria, CPS1, estados, CRC, zip, ROMs, PNG: utilidades sin máquina), `sf2_recomp` (el C
  generado y `dispatch.c`), `sf2_core` (vídeo, sonido, máquina, fachada; enlaza `ymfm`), `sf2_hostio` y `sf2_config`
  (plataforma), `sf2_harness` y `musashi` (solo validación). La separación evita que el paso cerrado (que trae sus propios
  ganchos `rt_*`) arrastre la máquina del núcleo al enlazar.
- **Recompilador como paso de la compilación** (`cmake/SF2Pipeline.cmake`): `interleave.py` (zip o carpeta, por CRC) →
  `rom.bin`; `dump_cycles` (tabla de ciclos de Musashi, construido en el mismo árbol) → `cycles68000.bin`; `gen_c.py` → 16
  archivos `.c` más tabla y cabecera. Cada paso es una regla con sus dependencias (los scripts, `hints.txt`, las ROMs), así que
  cambiar el generador o las ROMs regenera y recompila lo justo. El C va a `<build>/generated`, nunca al árbol de fuentes (D5).
- **Compilaciones cruzadas** (`cmake/SF2Generation.cmake`): Emscripten y mingw no pueden ejecutar `dump_cycles` ni Python
  con la tabla de Musashi compilada para el destino, así que el proyecto lanza un sub-proyecto nativo (`recompiler/host`) con
  `ExternalProject`, y el proyecto cruzado compila el C que éste deja en `<build>/hostgen/generated`.
- **Objetivos de validación**: `check`, `check-blind`, `run-blind`, `compare-mame`, `png-video`, `mame-video`, `compare-video`,
  `run-audio`, `wav-recomp`, `mame-audio`, `compare-sound-cmds`, `compare-audio`, `analyze`, `dasmcheck-run`, `run-video`:
  los mismos comandos del Makefile original como `add_custom_target`, con las referencias de MAME como reglas con
  dependencias (una referencia solo se regenera si cambian el script de Lua, las entradas o la lista de cuadros).
- **Makefile**: envoltorio. `make`, `make check`, `make compare-audio`... configuran `build/` y construyen el objetivo del
  mismo nombre; conservan `ROMDIR`, `BFRAMES`, `FRAMES`, `INPUTS`, `VFRAMES`. Además `make test` y `make web`. Se descartó
  mantener las reglas antiguas en paralelo (D36).
- **`generated/` de la raíz** (salida del Makefile antiguo) ya no se usa; la regeneración va a `build/generated`.

## Comandos

```bash
tools/setup-local-tools.sh cmake        # (ya hecho aquí)
export PATH=$PWD/external/cmake/CMake.app/Contents/bin:$PATH
cmake -S . -B build -DSF2_ROM_DIR=$PWD/sf2.zip        # configurar: 4,5 s
cmake --build build -j8                               # recompilar, compilar y enlazar: 19 s en un árbol vacío (8 núcleos)
make ROMDIR=sf2 all                                   # lo mismo por el envoltorio, con la carpeta de ROMs sueltas: 21 s
```

## Resultados

**El CMake da exactamente lo mismo que el Makefile original.** Antes de tocar nada se guardaron las huellas del Makefile del
hito 4 (`make run-blind`, `wav-recomp`, `png-video` y la lista de comandos de sonido, 12.000 cuadros) y se compararon con

| resumen por cuadro `summary_recomp.txt` | `29339a91e41a2beaa0d0e2f5b1eea5117b44f5a52991f991917b70989cef6cb6` | igual (también con `--step`, ver el paso de núcleo) |

| 17 PNG (`VFRAMES`) | 17 hashes | los 17 iguales (también los que escribe el juego `sf2`) |

Las comprobaciones de los hitos anteriores, ejecutadas **desde el build de CMake en un árbol vacío** con las referencias de

Los mismos objetivos (más `check-blind`, `png-video`, `wav-recomp`, `run-audio`, `analyze` y `dasmcheck`) se ejecutaron luego a través del

Tiempos: configurar 4,5 s; construir todo desde cero 19 s (generación de C incluida, 8 núcleos); recompilar tras tocar
`runtime/mem.c` 1,7 s (el C generado no se recompila).
